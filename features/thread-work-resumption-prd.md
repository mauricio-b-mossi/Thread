# Thread PRD For Ralph: Local Work Resumption Desktop App

This feature builds Thread, a Windows-first local desktop app for resuming work context across days. Thread is not a normal todo app. It is an external working memory that launches on startup, shows the user what to resume, lets the user pick exactly one active task, hides the main window, and keeps a small always-on-top floating task window on the desktop. The floating window uses a slowly looping donut as the only active-time proxy. While a task is underway, no numeric elapsed timer may appear in the floating window.

The required product shape is Tauri 2 with Svelte and TypeScript on the frontend, Rust for native commands, and SQLite for local persistence. The app must work fully offline, require no account, make no network calls during normal app use, and use a minimal Notion-inspired light palette. The core data model is tasks, sessions, task_events, and settings. A task has kind pickup or long_term, status pickup, backlog, active, completed, or archived, optional next_action, priority, and timestamps. A session has task_id, started_at, ended_at, duration_seconds, end_reason, progress_note, next_action, lap_duration_seconds, and recovery metadata. Exactly one active session may exist at a time.

The user experience is: start PC, Thread opens the Today window, user sees Pickup, Recent Threads, Backlog, and Quick Capture, user starts one task, Today hides, floating window appears above everything, donut fills clockwise once per 60 seconds by default, each new revolution changes muted color, user clicks the floating window to Continue, Complete, Stop/Pause, Switch Task, or Open Today, and stopping captures progress plus next action so tomorrow has context. Pickup tasks are short-term completion-oriented work. Long-term backlog tasks are durable projects that can be temporarily pulled into focus and then returned to backlog with a session note.

Visual design must be quiet and Notion-like. Use neutral colors such as app background #F7F6F3, surface #FFFFFF, subtle surface #FAFAF8, primary text #37352F, secondary text #787774, muted text #9B9A97, border #E6E4DE, hover #EFEDE8, and selected #E9E7E1. Donut colors should be muted, for example #7C9885, #6E8FA3, #B58A8A, #B69B63, #8E83A8, #A98274, and #65756A. Avoid saturated colors, decorative gradients, gamified streak UI, orbs, blobs, hero sections, and loud animations.

The acceptance standard for the complete feature is that a Windows user can launch the app, create pickup and long-term tasks, start either type, see the floating always-on-top window, see the donut revolve once per 60 seconds without any explicit active timer text, stop or complete tasks with correct lifecycle behavior, recover unfinished sessions after restart, and keep all data locally in SQLite across app restarts.

## Task 01: Scaffold The Tauri Desktop App

Create the greenfield desktop app foundation in this repository using Tauri 2, Svelte, TypeScript, and Rust. Set up package scripts for development, building, and testing. Establish a basic app shell with a Today window route or entry point and a placeholder floating window entry point if the framework needs separate frontend routes. Add a neutral global stylesheet with CSS custom properties for the Notion-inspired palette described in the feature overview. Configure the app name as Thread and keep the initial surface compact and utility-like, not a landing page.

Acceptance for this task is that the app can be installed or run in development mode, the main window opens to a basic Thread Today shell, and the codebase has a clear frontend and Tauri source layout. Testing for this task should include the normal scaffold build or type check that is practical in the environment, plus a short note in the task result if any platform dependency prevents running the desktop shell.

## Task 02: Implement SQLite Persistence And Migrations

Add local SQLite persistence from the Rust side. Implement a migration system and create the tables tasks, sessions, task_events, and settings. Store timestamps as ISO 8601 UTC strings. The tasks table must support id, title, description, kind, status, priority, pickup_date, next_action, sort_order, created_at, updated_at, completed_at, and archived_at. The sessions table must support id, task_id, started_at, ended_at, duration_seconds, end_reason, progress_note, next_action, lap_duration_seconds defaulting to 60, recovered_from_crash, created_at, and updated_at. The task_events table must capture task lifecycle events. The settings table must store key, value, and updated_at. Insert default settings for startup launch, Today-on-startup, donut lap duration 60 seconds, notion_light theme, floating window always-on-top, floating window position, long-term stop requirements, and return-to-Today behavior.

Acceptance for this task is that the app creates or opens the SQLite database in the standard app data location, runs migrations idempotently, inserts default settings once, and exposes Rust data access functions with tests for migration creation and basic CRUD. Tests should verify that a new database contains all expected tables and settings and that task/session rows round-trip correctly.

## Task 03: Add Typed Tauri Commands And Frontend Client Wrappers

Expose the core backend behavior through typed Tauri commands and matching TypeScript wrappers. Required commands are createTask, updateTask, archiveTask, listToday, listBacklog, listRecentThreads, startSession, getActiveSession, completeSession, stopSession, switchTask, resolveSessionRecovery, getSettings, updateSettings, saveFloatingWindowPosition, exportDatabase, and openDataFolder. Define shared frontend types for TaskKind, TaskStatus, EndReason, Task, Session, ActiveSession, TodayPayload, RecentThread, Settings, and each command input/result. Use explicit validation errors rather than silent failures.

Acceptance for this task is that the frontend can call the command layer without using ad hoc stringly typed payloads, commands return predictable data shapes, and invalid lifecycle operations return useful errors. Tests should cover command-level behavior where possible, especially createTask, getSettings, and validation of invalid task kinds or statuses.

## Task 04: Build The Today Window

Build the main Today window as the startup command center. It must have a compact header with the Thread name and a settings affordance, a Pickup section, a Recent Threads section, a Backlog section, and Quick Capture controls for creating pickup and long-term tasks. Empty states should be sparse and calm: Nothing queued for pickup, No recent sessions yet, and No long-term tasks yet. Task rows should show title, optional next action, and subtle metadata, but they should not be checkbox-first. Starting a task is the primary row action. The Today payload ordering should put active work first, then due pickup tasks, then recently updated or higher-priority items, with Recent Threads ordered newest first and Backlog preview focused on high-priority or recently touched long-term work.

Acceptance for this task is that users can create both task kinds, see them in the correct sections, select a task to start, and see stable empty states. The UI must use the neutral palette, avoid nested card-heavy layouts, and remain readable at the minimum practical window size. Tests should cover Today payload rendering, task creation from Quick Capture, and empty-state rendering.

## Task 05: Implement Session Lifecycle Rules

Implement the lifecycle rules for pickup and long-term tasks. Starting a pickup task creates an active session, marks the task active, hides Today, and opens the floating window. Completing a pickup task ends the session, stores internal duration, marks the task completed, sets completed_at, and removes it from Pickup. Stopping a pickup task ends the session, optionally stores progress and next action, and defaults to keeping the task in Pickup unless the user chooses backlog, archive, or complete. Starting a long-term task creates an active session and temporarily marks it active. Stopping a long-term task must require both progress note and next action, then return it to Backlog unless the user chooses to add it to Pickup. Completing a long-term task must require explicit confirmation because it completes the entire durable task.

Acceptance for this task is that exactly one active session can exist, task status restoration follows the product rules, invalid second-session starts are rejected or routed through switchTask, and the database records session duration only after session end. Tests should cover start, stop, complete, switch, long-term validation failure without note, long-term validation failure without next action, and pickup default stop behavior.

## Task 06: Create The Floating Always-On-Top Task Window

Implement the floating task window as a separate Tauri window that appears when a session starts and remains above normal desktop windows. The Today window should hide when a session starts. The floating window must show the task title, optional next action, and donut area, and it must not show a numeric active timer. It should be compact, draggable, and visually quiet, with a default width around 280px, height around 120 to 160px, subtle border, soft shadow, and border radius no larger than 8px. If no saved position exists, place it near the upper-right of the screen. Save final position after drag and reuse it for later sessions. Implement click versus drag so small pointer movement opens the action menu and larger movement drags the window.

Acceptance for this task is that starting a task hides Today, opens the floating window, keeps it always-on-top, shows the correct task content, allows dragging, persists position, and opens an action menu on click. Tests should cover click-versus-drag threshold logic as a pure function if possible, and manual verification should confirm the window stays above normal windows.

## Task 07: Implement The Donut Proxy

Implement the donut as the active-time proxy inside the floating task window. The default lap duration is 60 seconds, which means the ring fills clockwise from empty to full once per minute. After each full revolution, the ring resets to empty and continues with the next muted color in the palette. The calculation is elapsed_seconds from the active session start modulo lap_duration_seconds, with lap_index selecting the color. The donut must use smooth animation without flashing, pulsing, urgent states, sound, or numeric labels. It may be SVG or canvas, with SVG preferred for crisp desktop UI. Add settings support for preset lap durations 30, 60, 90, and 120 seconds plus a custom range from 10 to 600 seconds.

Acceptance for this task is that the floating window displays a smooth donut, the default revolution is one minute, colors cycle per lap, settings change the lap duration, and no explicit active timer text appears while the task is underway. Tests should cover lap progress calculation, color cycling, and absence of active timer text in the floating window component.

## Task 08: Build Stop, Completion, Switch, And Recovery Flows

Build the user-facing flows for stopping, completing, switching, and recovering sessions. The floating action menu must offer Continue, Complete, Stop/Pause, Switch Task, and Open Today. Pickup stop should show optional progress note, optional next action, and destination choices defaulting to Pickup. Long-term stop must require progress note and next action, default to Backlog, and allow adding the task to Pickup. Switching tasks must stop the current session first and enforce long-term requirements before starting the selected task. If the app launches with a session whose ended_at is null, show a recovery prompt before normal Today: Resume, Stop and write note, or Discard. Resume reopens the floating window, Stop uses end_reason app_closed, and Discard sets end_reason discarded and excludes the session from history totals.

Acceptance for this task is that all action menu choices work, stop forms validate correctly, switchTask cannot lose notes for long-term work, unfinished sessions are detected on restart, and recovery decisions update both task and session state correctly. Tests should cover recovery resume, recovery stop, recovery discard, pickup stop destinations, long-term required fields, and switch behavior.

## Task 09: Add Settings, Startup Registration, Tray, And Data Utilities

Build the Settings view and related native utilities. Settings must include launch on startup, show Today on startup, donut lap duration, theme display, reset floating window position, export database, and open data folder. Implement Windows startup registration through Tauri or native APIs and show a clear failure state if registration fails while keeping the app usable. Add a system tray menu if supported cleanly, with Open Today, Show Floating Task, Stop Current Task, Settings, and Quit. Quitting while active should preserve the unfinished session for recovery rather than silently completing it. Export database should create a backup copy without deleting or replacing the original.

Acceptance for this task is that settings persist in SQLite, startup registration can be enabled and disabled, tray actions work where supported, export creates a backup, and open data folder opens the local app data location. Tests should cover settings persistence and command behavior; manual verification should cover startup registration and tray behavior on Windows.

## Task 10: Add History, Task Detail, And Recent Threads Polish

Implement secondary history and task detail surfaces. Task detail must show title, description, kind, status, current next action, total historical active time, session history, progress notes, and complete/archive controls. Recent Threads in Today must show recent stopped or completed sessions with progress note, next action, relative date, and historical duration. Historical durations may be visible here because the task is no longer actively underway. Discarded sessions should either be hidden from normal history totals or clearly excluded. Completed and archived tasks should not clutter Today by default.

Acceptance for this task is that users can inspect what they worked on, see where they stopped, and recover next actions from recent sessions or task detail. Tests should cover recent-thread ordering, exclusion of discarded sessions from totals, and task detail data rendering.

## Task 11: Apply Visual Polish And Accessibility Pass

Polish the UI so it feels like a calm Notion-inspired desktop utility. Ensure neutral palette usage is consistent, focus states are visible, text fits at minimum window sizes, task rows remain dense but readable, floating window content does not overlap, and the active donut is visually calm. Add keyboard behavior where practical: N for new task, slash for search/filter, Enter to start selected task, Escape to hide Today or close menus, Ctrl+Comma for settings, and Ctrl+Enter to submit stop forms. Keyboard support is additive and must not make mouse interaction worse.

Acceptance for this task is that the app looks cohesive, avoids loud or gamified visuals, works at minimum window size, and supports the core keyboard paths without layout breakage. Manual QA should include desktop and smaller window sizes, floating window positioning, action menu fit, stop form fit, and keyboard navigation.

## Task 12: Final Verification, Packaging, And Documentation

Run the final verification pass for the complete product. Verify cold launch, first-run empty state, creating pickup and long-term tasks, starting each task type, floating always-on-top behavior, donut default one-minute revolution, donut color cycling, no explicit active timer in floating window, pickup completion, pickup stop, long-term stop with required note and next action, recent threads, recovery after forced app close, settings persistence, startup registration, database export, and local persistence across restarts. Add concise README documentation describing the product, local-first storage, development commands, and current limitations. Package a Windows build if the environment supports it.

Acceptance for this task is that configured checks pass, the README is accurate, the manual acceptance checklist is completed in the task result, and any environment-specific packaging limitation is clearly reported. The final app must satisfy the feature overview and must not introduce cloud sync, accounts, telemetry, active numeric timer text, or decorative/gamified design.
